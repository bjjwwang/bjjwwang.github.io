一个宏伟的计划，和它遭遇的第一堵墙

Created on March 29, 2026

2026   ·   SVF   Static Analysis   Tree-sitter   Compilers   ·   research

所有宏伟的计划，在遇到第一个技术细节之前，都显得无比美好。

计划是这样的

我有一个宏伟的计划。

SVF——我们实验室做的静态值流分析框架——现在只能分析 C/C++，因为它深度依赖 LLVM 的编译产物。你得先把代码编译成 LLVM IR，SVF 才能工作。这件事在学术界没什么问题，但在工业界就有点尴尬：你让一个用 Python 写代码的人先装 Clang 再编译再分析？

于是我有了个想法：用 Tree-sitter 替换 LLVM，实现不需要编译就能分析代码。 Tree-sitter 是 GitHub 开发的通用解析器，支持 40+ 种语言，只需要源码就能生成语法树。如果 SVF 能直接吃 Tree-sitter 的输出，那它就能分析 Python、JavaScript、Rust……理论上，任何语言都行。

更大的图景是：把这样的 SVF 封装成一个工具，接入 Cursor 这样的 AI 编程助手，让大模型在帮你写代码的时候，能实时调用精确的静态分析。AI 写的代码有没有内存泄漏？有没有空指针？有没有数据竞争？让 SVF 来回答，而不是让模型猜。

这个愿景很美好。然后我开始认真研究它……

然后，现实出手了

核心问题是：Tree-sitter 只是个解析器，它只告诉你代码的物理结构，不告诉你任何语义。

SVF 的工作原理是构建一系列复杂的图——指针赋值图（PAG）、值流图（VFG）、过程间控制流图（ICFG）——然后在这些图上做分析。而这些图的构建，依赖大量 LLVM IR 提供的语义信息：变量是 SSA 形式的，类型是明确的，控制流是规范化的，符号已经解析好了。

Tree-sitter 给你的是啥？一棵忠实于源码的具体语法树（CST）。for 是 for，await 是 await，@decorator 是 @decorator。每种语言的语法构造，在 Tree-sitter 眼里都是不同的节点，没有统一的语义。

这意味着，你不只是换了个前端，你是要在一片荒野上重新盖一栋楼。

具体有哪些难？

研究下来，主要是四堵墙。

第一堵墙：动态类型

Python、JavaScript 这类语言，变量没有固定类型。x = 1 然后 x = "hello" 是完全合法的。SVF 的指针分析需要知道”这个变量可能指向哪些对象”，但当类型在运行时才确定时，静态分析必须用过度近似——保守地假设所有可能性都存在。

更头疼的是 JavaScript 的属性访问。obj[prop_name] 里的 prop_name 如果是个变量，你根本不知道访问的是哪个属性。指针分析只好假设”可能是对象的所有属性”，精度直接崩了。

第二堵墙：垃圾回收

SVF 有一个很有用的 Saber 检测器，专门找内存泄漏。逻辑很简单：分配了但没释放的内存，就是泄漏。

但 Java、Python、Go 都有 GC，内存的释放不由程序员控制。”分配-释放”这个模式不存在了，传统的内存泄漏检测失去意义。分析目标要从”有没有忘记 free”变成”有没有不必要地持有引用太久”——这是完全不同的分析框架。

第三堵墙：语法糖

这是让我觉得 Tree-sitter 的局限最直接的一点。

不同语言里，语义上等价的操作，语法上千差万别：

  • let [a, b] = arr（解构赋值）→ 本质是两次数组读取
  • await func()（异步等待）→ 本质是创建一个状态机
  • try...catch（异常处理）→ 本质是带条件跳转的控制流

LLVM 的工作之一就是把这些都”脱糖”成统一的 IR。Tree-sitter 不做这件事——它只是如实记录你写了什么，await 就是 await，不会帮你变成状态机。

所以基于 Tree-sitter 的前端，必须自己实现一个”脱糖层”，为每种语言的每种语法糖写处理逻辑。40 种语言，每种几十个语法构造……这个工作量，是真实的。

而且脱糖之后还有个”重糖”问题：当 SVF 在内部的中间表示上发现 bug，怎么把报错位置映射回原始源码？用户可不想看到指向”他从未写过的中间代码”的报错。

第四堵墙：语言原生的安全机制

Rust 有所有权系统和借用检查器，在编译时就排除了绝大多数内存安全问题。对 SVF 来说，这意味着可以做更激进的”强更新”分析——因为语言本身保证了没有别名。

但 Tree-sitter 不提供这些类型信息。如果 SVF 用 Tree-sitter 前端分析 Rust，它看不到借用检查的结果，反而要重新推导 Rust 编译器已经算好的东西——而且可能推导得还不如编译器准确。

那 Tree-sitter 解决了什么？

Tree-sitter 解决了解析这件事——把源码变成结构化的语法树，支持增量更新，容错性很好，速度很快。

这很有价值，但它只是整个问题的一小部分。

从语法树到可以做精确分析的图，中间还需要：

  • 符号解析（这个变量指的是哪个定义？）
  • SSA 构建（每个变量在每个程序点的值是什么？）
  • 类型推导（特别是动态语言）
  • 脱糖（把各种语法糖降低到统一的语义原子）
  • 内存模型建模（堆、栈、GC……每种语言不一样）

Tree-sitter 帮你完成了第零步。剩下的，都得自己来。

路在哪里？

并非没有出路，只是比想象的更长。

研究界有几个方向值得借鉴：

Stack Graphs（GitHub 开发）提供了一套声明式 DSL，可以为不同语言定义名称绑定规则，从 Tree-sitter 的语法树出发构建符号解析图。它解决了”这个变量是哪里定义的”这个问题。

Braun 算法可以直接从 AST 构建 SSA 形式，不需要先经过 LLVM。这为脱离编译器构建值流分析提供了可能。

结合这两者，加上针对每种语言的脱糖层，理论上可以构建一个语言无关的 SVF 前端。只是工程量非常大，而且每种语言都有自己的坑。

结语

这个计划还在路上。

Tree-sitter 确实打开了一扇门——”解析”这件事，不再是障碍。但静态分析真正困难的地方，在解析之后才开始。

也许更务实的路径是：先把 SVF 接入 Cursor，但只支持 C/C++，先让 AI + 精确静态分析的组合在一个语言上跑通；同时，慢慢地把多语言支持的地基一点点垫起来。

宏伟的计划，一步一步来。
